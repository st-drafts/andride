# Rendering performance

Version 1.46 reuses numerical analysis for the same FIT object and relevant profile values. WeakMap entries retain only the latest variant: changing FTP, maximum heart rate, rider mass or bike mass invalidates the respective calculation. Replacing a ride on import, route edit or history refresh invalidates all its cached results. Do not mutate FIT objects in place or mutate returned results. Original readings, zero cadence and missing sensors are unchanged.

Overview shares one coachPlan between its goal story, history summary and schedule. History dates are formatted once per ride per calculation. Translation results are bounded to 4096 short strings; loading a language pack clears fallback results. DOM localization skips text and attributes only when both the current output and selected language match the previous pass.

Synthetic benchmark: 100,000 one-second records, ten repeat calculations on the same object, compared with published 1.45. Heart-rate zones averaged 3.46 ms before / 0.0081 ms after; power and energy 5.20 ms / 0.00125 ms. Numerical outputs were deep-equal. Timings are machine-specific and describe warm calculations, not total startup or first analysis latency.

## Release review — 1.49

Opening a ride no longer calculates best efforts, distance records and route matches for every historical FIT before displaying the main narrative. Those sections load on disclosure. Historical effort calculations yield after approximately 8 ms of accumulated work, cancel on navigation/closure and release temporary interval caches while keeping compact record results. Route signatures and cumulative-distance arrays are reused.

A synthetic cold-render comparison with published 1.48 used 21 rides / 151,221 points. Four fresh-input runs per version alternated execution order. Median JavaScript markup time was 204.28 ms before / 15.01 ms after. This measures the analysis markup function in Node, not total browser startup, DOM layout or mobile performance. The historical comparison work is deferred, not removed; large individual recordings can still take time when a comparison is requested.

Batch import keeps successfully committed parsed rides in memory instead of re-reading every stored FIT after each file. Logging failure cannot hide a completed import. IndexedDB opens share a pending connection promise, backups read rides/files/metadata in one readonly transaction, and deleting a session reads sibling keys instead of cloning the entire history. Backup restore calculates merged metadata before its transaction, and publishes new state only after commit. Coach history is deduplicated before applying storage limits.

Native IndexedDB checks were run on an isolated localhost origin: shared connection, original/session atomic import, duplicate import, transaction rollback, consistent backup snapshot, preserving an original for remaining sessions, removing an orphaned original. Browser restore checks rejected a bad checksum and accepted a valid additional FIT/goal while preserving previous data. The reproducible harness is tests/browser-storage.html; copy it into a built dist directory as release-storage-qa.html with a synthetic release-qa.fit. It refuses to run on nonempty storage. Never point it at a user's data.

Scope and remaining acceptance limits: this is a review of first-party logic with synthetic regression and desktop-browser checks, not an audit of vendored Garmin/MapLibre internals. iOS standalone installation/eviction and Android hardware gestures still require physical-device smoke testing before a public launch. Weather, satellite tiles and new terrain elevations require a network; saved FIT, analysis, planning and saved corrected routes remain local. Existing restore limits remain 200 MB / 300 original files; very large libraries need an explicit backup-size strategy before supporting them at launch.

Landmarks now default to off unless the user has explicitly enabled them. This avoids automatic Wikipedia queries with rounded route coordinates and saves requests while opening a ride. Existing explicit enable/disable choices remain unchanged. The existing Landmarks button is the opt-in control; no additional dialog is introduced.
